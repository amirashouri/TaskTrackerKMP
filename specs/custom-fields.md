# custom-fields — per-project custom fields on work items

- **status:** pending
- **priority:** P1
- **context:** Derived from a review of `WorkItemEditor` (2026-11-06): the editor is limited to
  a fixed field set, so teams whose work does not fit `title/details/points/priority/due/tags`
  cannot bend the tool to their process. This is a **cross-repo wire change** — read
  `../AGENTS.md` §1/§2 before starting; it needs a Phase 1 `ACK`, and the server lands first.
  The server side is tracked in `TaskTrackerServer/specs/custom-fields.md`.

## Scope

Client modules for the definition (project) and the value (work item): `:packages:domain`,
`:packages:database`, `:packages:feature-projects-{domain,data,presentation}`, and the network
DTOs layered on top of `:packages:network`. No change to tags, hierarchy, or time tracking —
those are separate specs.

## Files

`to confirm at Phase 1` — the plan below names candidate anchors, not an agreed diff.

- `packages/domain/src/commonMain/kotlin/com/tasktracker/domain/Entities.kt` — add

- `packages/feature-projects-presentation/src/commonMain/kotlin/com/tasktracker/featureprojectspresentation/workitem/WorkItemEditor.kt`

- `packages/database` + `packages/feature-projects-data` — storage (JSON column or join table)

- `packages/feature-projects-data/**/remote/*` — decode/encode the new keys.
- Server (owned by its spec): `internal/entities`, `internal/db/migrations` (both dialects),
  `cmd/server`, `docs/API.md`, `cmd/server/contract_test.go`.

## Contract

- [ ] A project admin can define ordered, typed fields (at least Text, Number, Date,
  Single-select, Multi-select, Checkbox); the catalog is project configuration like tags.
- [ ] A work item exposes and persists values for those fields, offline-first (outbox), and
  they survive a push/pull round-trip.
- [ ] Values for fields the project no longer defines are dropped on read, exactly as stale
  tag ids are (`WorkItemEditorModel.retainedIn`).
- [ ] Decoding is client-first: the client declares the new fields **with defaults**, so an
  older server that omits them still decodes (`ignoreUnknownKeys` stays off).
- [ ] Reverting the client change fails a focused test that pins the new field.

## Non-goal

- [ ] Not a rename of `tags`, and not cross-project/shared fields.
- [ ] No field-level permissions or per-role visibility.
- [ ] No formula/rollup fields.

## Validation

- Run: `./gradlew --offline :packages:<module>:jvmTest --tests '<pattern>'` for each touched
  package (domain round-trip, database mapping, editor model, save path); focused, under a
  minute. Server: `go test ./internal/...` per its spec.
- Cross-stack: a push/pull round-trip proves the wire pair; the server's
  `cmd/server/contract_test.go` pins the client's declared key set.
- Counts: `test-baseline.json` moves on the JVM host; regenerated by a release
  `scripts/check.sh full`, not the focused run.
- Pixel-reading is out of scope for the model/storage layers; if the editor adds a rendered
  control, its pixel test goes through `test-reviewer`.

## Risks / notes

- A JSON blob column is the cheap storage shape but harder to query/validate; a join table is
  the opposite. Decide in Phase 1, not per-layer.
- Multi-select ordering and single/multi cardinality are the two spots most likely to drift
  between Go and Kotlin serialization.
