## Design decisions

- **Raw key, not `DefaultsKey`.** `UserDefaultsStore.removeAll()` runs on sign-out and
  walks `DefaultsKey.entries`. A server address is a property of the device, not the
  session; losing it on sign-out would make the customer re-enter it. The store already
  has a verbatim raw-key path for exactly this case, so no `DefaultsKey` member is added
  and `UserDefaultsStore` itself does not change.
- **`runBlocking` in the resolver.** `platformApiBaseUrl` is called before the graph
  exists and must synchronously decide which HTTP clients to bind. The read is one small
  preference, and the store's suspend functions only suspend for a mutex with no
  contenders at startup. An unreadable store falls back to the build-time value rather
  than refusing to launch.
- **Restart required.** The URL is resolved once, while `AppGraph` binds the app-scoped
  HTTP clients. Changing it later cannot reconfigure them without tearing down the graph
  and its services, so a saved change takes effect on the next launch. 6.2 must surface
  that expectation in Settings.

## Contract

- [x] With no override, every host returns exactly what it returns today — the three
      existing `PlatformApiBaseUrl` tests stay green and unmodified.
- [x] A persisted override wins over the build-time value on all three hosts.
- [x] A blank or whitespace-only override is treated as unset and falls back, matching the
      existing `takeIf { it.isNotBlank() }` rule; it must not produce a `URLBuilder` with
      no scheme.
- [x] The override survives sign-out (the decision above), and the test names that
      explicitly — a change that moved it into `DefaultsKey` would otherwise pass a
      "persists" test and fail this one.
- [x] Removing the override restores the build-time value without an app restart, **or**
      the spec records that a restart is required and why. Recorded above: the URL is
      resolved once while `AppGraph` binds the app-scoped HTTP clients.
- [x] The override is part of what `platformApiBaseUrl` returns, so the existing local-network
      classification and the Android permission request cover it. An override saved to
      `10.0.2.2`, an RFC1918/CGNAT address or an mDNS name must not produce a silent timeout —
      see [`android-local-network-permission.md`](android-local-network-permission.md).

## Risks / notes

- **A local override needs a permission, not just a URL.** On Android 17 a root on the local
  network (`10.0.2.2`, RFC1918, CGNAT, an mDNS name) is unreachable without the runtime
  `ACCESS_LOCAL_NETWORK` grant, and the failure is a timeout rather than a refusal — measured,
  and recorded in [`android-local-network-permission.md`](android-local-network-permission.md).
  Keeping the override inside `platformApiBaseUrl` is what keeps it covered by that gate.
- Easy to get wrong: storing the URL where the auth tokens live, or in `DefaultsKey` when
  sign-out clears it. Both are silent — the app simply asks for the server again.
- This task has no server dependency and can land before any of `T9.4`–`T9.10`. Doing so
  is the point: it makes the client ready before the CLI has something to point it at.
