## Scope

The Settings surface for the runtime API root: a row that shows the address the app is
using, a sheet that edits it, and a reset-to-default action. It is the caller of 6.3's
validator/probe and the writer of 6.1's raw preference key.

Modules: `:packages:feature-settings-domain` (the port and its value), 
`:packages:feature-settings-data` (`LiveSettingsService` over the preference),
`:packages:feature-settings-presentation` (model, row, sheet, screen),
`:packages:design-system` (strings only), `:composition-root` (wiring the probe and the
in-use root), `:shared-ui` (binding the model to the screen). No server change, no
wire-format change, no Room change.

## Design decisions

- **The write is the validator's caller, not a copy of its rule.** `setServerAddress`
  validates *and* probes (`CheckServerAddress`) inside the data layer, and only persists a
  `Valid`, normalised `baseUrl`. A model that had to remember to validate first could
  forget; making the port method the whole operation makes "saved" mean "checked".
- **The in-use root is what the row shows; the saved override is what it will use next
  launch.** 6.1 resolves the root once, while `AppGraph` binds the app-scoped HTTP
  clients, so a saved change cannot reconfigure them in this process. The row therefore
  shows `inUse` (the address actually on the wire) and a save/reset raises a restart
  notice rather than pretending the change is live. `savedOverride` is only used to
  prefill the field and to decide whether Reset is offered.
- **The model owns the editor, the screen owns the wording.** `ServerAddressEditor`
  (draft, checking, failure) and `ServerAddressNotice` (Saved/Reset) are plain values, so
  the model stays testable without a composition; the screen maps `Reason` and the notice
  to strings it reads from the design system. The `when` over `Reason` is total, so a new
  reason is a compile error here.
- **`inUse` may be `null`.** `testBindings` builds the graph with no backend (the offline
  demo); the row shows a "no server" string rather than inventing a URL. Saving from the
  demo still writes the preference, which the next launch's shell reads through 6.1.
- **Saving while the sheet is open is cancellable only by leaving Settings.** The probe can
  take its 5 s; leaving Settings cancels the call, and the model rethrows
  `CancellationException` the way `signOut` does, so no notice is raised for a screen that is
  gone. Dismissing the sheet does **not** cancel the shell-scoped call, so Reset and Cancel are
  disabled while `isChecking` — otherwise Cancel would hide a save that still lands and Reset
  would race it.
- **Reused primitives only.** The sheet is `TTBottomSheetScaffold`; the row uses the
  design-system type/colour helpers. No new glass token, so no Phase 1 token mapping is
  required.

## Contract

- [x] The settings screen shows a Server row whose value is the address currently in use
      (`ServerAddressSettings.inUse`), or a "no server" label when it is `null`.
- [x] Opening the row shows a sheet whose field is prefilled with the saved override if
      one exists, otherwise with the in-use address.
- [x] Saving a valid, reachable address persists the normalised value under
      `API_BASE_URL_PREFERENCE_KEY`, closes the sheet, and raises a restart notice; the
      row still shows the in-use address.
- [x] Saving an address `CheckServerAddress` rejects persists **nothing**, keeps the sheet
      open, and shows the matching failure text; the stored override is unchanged.
- [x] Reset is offered only when a saved override exists; it removes the key and raises a
      restart notice. The stored override reads back as `null`.
- [x] `serverAddress()` reports the injected in-use root and the current raw override, and
      treats a blank stored value as no override.
- [x] Every `ServerAddressValidation.Reason` maps to a distinct string (total `when`).
- [x] While a check is in flight, Save shows the busy state and Reset and Cancel are
      disabled, so the dispatched save cannot be dismissed into a contradictory notice.
- [x] Nothing in `:packages:feature-settings-domain` reads a resource or a platform API;
      the model is constructible in a plain test with no composition.
- [x] The property still holds when the production change is reverted: with the row's
      click removed the sheet cannot be opened; with validation skipped an invalid address
      is persisted (Rule 1).

## Risks / notes

- `UserDefaultsStore.set(String, String)` returns `true` unconditionally, so a failed
  preference write is not representable. A `Valid` result therefore means "checked and
  written"; the storage layer logs its own write failures. If a write ever needs a
  failure path, `ServerAddressValidation` has no reason for it yet — do not invent one
  without a second ACK.
- The row is new UI in `:shared-ui`'s largest file's binding path; edit
  `NavigationHost.SettingsDestination` deliberately, not by script.
- `HttpServerAddressProbe()` builds no engine at construction (the engine is built per
  probe inside `KtorProbeClient`), so wiring it into `registerSettings` keeps graph
  construction free of platform calls, which `HostedGraphScenarios` asserts.
