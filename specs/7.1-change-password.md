## Change Password Flow

### When the user chooses to change their password

The Settings screen's **"Change Password"** row opens `ChangePasswordSheet`:

1. A **"Verify with: Old Password | Admin Code"** segmented selector (the design
   system's `TTGlassSegmentedPicker`) decides which credential the form asks for;
   swapping it clears the credential field, because a password left in a code field
   would be read as the wrong kind of thing.
2. Fields: the credential (masked), the new password (masked), the confirmation.
3. Client-side validation mirrors the server's policy — at least 8 characters,
   matching confirmation, non-empty credential — so a typo never becomes a round trip.
4. On submit the sheet dispatches one model command, which calls the port with **both
   halves** of the body.

### Port extension

`:packages:feature-settings-domain` — `SettingsPort`:

```kotlin
@Throws(AppError::class, CancellationException::class)
suspend fun changePassword(newPassword: String, oldPasswordOrCode: String)
```

`:packages:feature-settings-data` — `UserProfileGateway` gains the same method
(delegated to by `LiveSettingsService.changePassword`; a `null` gateway — the offline
demo — throws `AppError.Validation("There is no account on a server…")`), and
`HttpUserProfileGateway` answers it with **`POST /v1/me/password`**:

```json
{ "old_password_or_code": "either-the-old-password-or-the-reset-code",
  "new_password": "the-proposed-new-password" }
```

→ `200 {"id","email","display_name","password_hash"}`. The route is **not**
`PATCH /v1/me`: that route is the shipped profile write the client already decodes
(`specs/settings-user-backend-profile.md`), so the action gets its own path. The POST
is deliberately **not** replayable — success consumes the credential.

A refusal arrives as `AppError.Validation` carrying the server's own sentence (`400`
is in `HttpErrorMapping`'s surface-safe set): wrong credential, spent/expired code, or
password policy.

### Model

```kotlin
sealed interface ChangePasswordOutcome {           // sealed, not the enum the first
    data object Started : ChangePasswordOutcome    // draft sketched: Failure carries
    data object Success : ChangePasswordOutcome    // an AppError, which an enum entry
    data class Failure(val error: AppError) : ChangePasswordOutcome
}

suspend fun requestChangePassword(newPassword: String, oldPasswordOrCode: String)
fun dismissChangePasswordOutcome()
```

`CancellationException` is rethrown, not held — a sheet disposed mid-submit must not
arm a banner over the next screen.

## Forgot Password Flow

**There is no self-service request, and that is the flow rather than a missing
piece.** The project owns no mail infrastructure (`AGENTS.md §7`): no endpoint emails
a member, so a code can only come from an admin who mints one. An endpoint that minted
a code to whoever asked — from inside their own signed-in session — would let a session
that already holds the account reset its password without the old one, which is exactly
what requiring the old password *or* an out-of-band code prevents.

1. The **"Forgot Password"** row opens `ForgotPasswordSheet`: instructions ("ask your
   workspace admin to generate a one-time code… expires after 24 hours, usable once")
   and one CTA, **"I have a code"**, which closes this sheet and opens the change sheet
   with the selector already on **Admin Code**.
2. The member's admin generates the code from **Members → the member's row → the
   padlock** (`MemberAdminPort.generateResetCode(id): String`, answered by
   `POST /v1/admin/users/{id}/password-reset-code`, whose response is
   `{"code","expires_at"}` — the code in the reply *is* the delivery).
3. The admin hands the code over out of band; the member enters it as the credential
   in the change sheet. The server consumes it on the change it authorises, so one
   code leads to exactly one new password.

## UI

- **ChangePasswordSheet** — selector, credential/new/confirmation fields, inline local
  refusals, the server's refusal verbatim, `Started` disables submit, `Success` swaps
  the form for "Your password was changed." + Done. Dismissing clears the model's
  outcome, so no stale banner greets the next open.
- **ForgotPasswordSheet** — instructions + "I have a code". Sends nothing.
- Rows carry tags `settings.changePassword` / `settings.forgotPassword`; both sheets
  and their controls have tags (`settings.changePassword.sheet`, `.credential`,
  `.new`, `.confirm`, `.submit`, … / `settings.forgotPassword.sheet`, `.haveCode`).
- Shell binding: `shared-ui/.../NavigationHost.kt` `SettingsDestination` passes
  `changePasswordOutcome`, `onRequestChangePassword`, `onDismissChangePasswordOutcome`.
  The row taps are local sheet opens, like `nameEditorOpen`.

## Admin half (cross-repo, same ACK)

`MemberAdminPort.generateResetCode(id)` → `HttpMemberAdminRemote` →
`POST /v1/admin/users/{id}/password-reset-code` (no body; member named by the route).
`MemberAdminModel` holds `resetCode: GeneratedResetCode(member, code)?` and
`isGeneratingResetCode`; failures land in the existing `listFailure` banner. The row's
padlock (live rows only, disabled while minting) opens a `ConfirmPopup` whose body
names the member, states single-use + 24h, and whose **Copy** puts the code on the
clipboard.

- **Gotchas:**
  - The client is the fixed point: `@SerialName("old_password_or_code")` /
    `new_password` / `code` / `expires_at` must match the Go `json:` tags byte for
    byte — Go matches case-insensitively, Kotlin does not.
  - `password_hash` is in the change-password response DTO only because
    `ignoreUnknownKeys` is off; it is never read.
  - The change-password POST is **not** idempotent and must not be opted in: success
    consumes the credential.
  - Password policy is 8 characters on **both** sides (`MinPasswordLength` in
    `ChangePasswordSheet.kt`, `minPasswordLength` in `internal/me/handler.go`); they
    are copies of one rule and must move together.
  - There is no mailer and none may be added for this flow (AGENTS.md §7); the admin
    dialog's Copy is the delivery.
  - The original draft of this spec sketched `validateResetCode`/`ResetToken` and a
    self-service `requestPasswordResetCode` — both were dropped under the ACK: the
    first has no server endpoint and burns the code before the password is set, the
    second needs email delivery that does not exist. Do not reintroduce them.
