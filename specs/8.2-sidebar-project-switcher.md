## Layout revision: one stack, groups by scope

8.1 + the first 8.2 pass composed `heading → LazyColumn(weight(1f)) → five
destinations`, and it was rejected after review for three reasons that are one
reason: **the only flexible gap sat in the middle of the navigation**, so the
four primary work destinations were bottom-anchored by accident. It also
composed `Projects` twice (section heading plus a destination row) and hung the
`SidebarButtonTag(AppTab.Projects)` on three nodes at once.

The panel is now a single top-aligned stack, ordered by scope, with the empty
glass below the last row rather than between two groups:

```
▣ Projects                    ← destination row: the index (selected wash when current)
   ● Product Roadmap      PR   ← switcher: name, then key prefix; dot marks the active one
     Mobile App           MA
     …
     Board                    ← the active project's views, indented under the list
     Backlog
     Sprints
 ⚙ Settings                   ← app-level, last
   (empty glass)
```

Rules that make it read as one panel and not seven peers:

- **Order is the hierarchy.** Index first, then the collection it opens, then
  the views of the collection's active member, then the app-level destination.
  `AppTab.entries` order is preserved inside the scoped group (Board, Backlog,
  Sprints) and `Settings` stays last, so muscle memory from the bar and the rail
  transfers.
- **The list is the only flexible child, and it wraps when short**:
  `weight(1f, fill = false)`. Non-weighted siblings are measured first, so the
  destinations can never be pushed off the panel (the 8.2 contract line this
  was already guarding), but two projects do not open a ~400dp void between the
  list and the rows that act on it.
- **One indent, two real gaps.** The scoped group is inset by `ttSpacing.lg`, and
  both group breaks are `ttSpacing.xl`. A row already carries 6dp of its own
  vertical padding, so a smaller spacer leaves the cross-group distance close to
  the distance between two rows inside one group — seven rows read as one list.
  No divider, no new token.
- **Project rows are text, not a repeated glyph.** The first pass drew the same
  `ttTabIcons.projects` glyph on every project at the destinations' own size and
  type, so two projects read as `Projects, Projects`. The row is now the name at
  `ttTypography.subheadline` with the key prefix trailing in `ttTypography.key`.
  The prefix is data the app already prints on work items (`AP-12`) and is what
  distinguishes two similarly named projects; it trails because a prefix is 2–10
  characters, and a leading column sized for ten would leave a ~66dp gutter in the
  common two-character case. The name holds the aligned left edge instead.
- **Two selection signals, because there are two states.** `ttSelectionWash`
  marks the current *view* only. The active *project* is marked by a dot in a
  reserved leading slot, with both labels in `selectedInk` and
  `semantics { selected }` for accessibility. The slot is reserved on every row,
  so the names keep one leading edge when the active project changes. One wash
  carrying both meanings made two rows look selected for unrelated reasons —
  that was the second complaint in review.
- **The project row is a button, not a tab.** It switches context and then
  lands on Board; `Role.Tab` described it wrongly.

## Contract

Every line below is covered by a scenario in `ShellScenarios`. `## Handoff` records which
scenarios were also mutation-checked.

### Switcher

- [x] The section lists exactly the **non-archived** projects, in
      `ProjectPickerModel`'s own order: `updatedAt` descending, then name. The
      first row is the most recently updated seed, pinned against a fixture
      where that is not the alphabetical first — otherwise an alphabetical list
      passes.
- [x] Exactly one project row is marked selected, and it is the active project.
      On first composition with no active project, no row is selected.
- [x] Tapping a row makes that project active and lands on **Board**, from any
      tab. Assert the `Board` destination and the row's `selected` property
      together, so a stale id or a tab that did not move both fail.
- [x] Tapping a project while **Settings** is selected still lands on Board.
      This is why the call is `openProject(id, AppTab.Board)` rather than the
      default: the router rejects Settings outright (`Router.openProject`'s own
      KDoc), and a switcher that silently does nothing on one tab is worse than
      one that moves.
- [x] The highlight follows a project chosen **elsewhere**: select a project
      from the Projects tab's own list at 1280dp, then assert the sidebar's
      selected project row moved. This is the assertion that fails if a second
      "which project" state is introduced.
- [x] An empty switcher renders no project rows, and all five destinations are
      still there. No placeholder, no empty-state copy. The fixture is an
      **archived** project rather than an empty store: the Projects list seeds a
      sample project when the store is empty, so an archived project — excluded
      from the picker, and enough to make the seed a no-op — is the only shape
      in which "no rows" is observable.
- [x] Forty projects scroll inside the list and never move the destinations: a
      destination row's bounds are unchanged before and after scrolling to the
      last project. Forty rather than twenty because the sidebar scenarios
      compose at a reduced density (see `## Handoff`), which gives a taller
      display in dp; twenty rows fit there, and a scroll that scrolls nothing
      asserts nothing.
- [x] Creating a project through the existing New Project sheet while the shell
      is up makes it appear without a relaunch (the model observes
      `ProjectChange`). The id is read back from the store, because the form
      returns nothing to its caller and a name search would also match the
      Projects list behind the sheet.

### Layout

- [x] The panel is one top-aligned stack: the `Projects` row is the topmost
      child, the project list is below it, `Board`/`Backlog`/`Sprints` are below
      the list and above `Settings`, and `Settings` is above the panel's bottom
      edge by more than one row — not pinned to it. The gap between the
      `Projects` row and `Board` is under 100dp, which is the measurement that
      distinguishes a top-aligned stack from the rejected bottom-anchored one
      (there the gap was several hundred dp).
- [x] The scoped rows share one left edge, inset past the project rows' — the
      indent is the nesting signal.
- [x] Project rows are visually distinct from destinations: name at
      `ttTypography.subheadline`, key prefix trailing in `ttTypography.key`, the
      active row marked by a dot in a reserved leading slot, and no repeated
      project glyph. The prefix is asserted per row, so the identifier cannot
      quietly disappear from the row while the tag and the name still pass.
- [x] Both group breaks are `ttSpacing.xl`: the edge-to-edge distance across a
      group is at least twice the distance between two rows inside one group, so
      the list and the views do not read as a single stack.
- [x] Every destination tag resolves to exactly one node. `Projects` in
      particular must not be a heading plus a row: a tag with three matches
      makes every tap-by-name scenario fail, and 8.1 shipped that shape.
- [x] The `Projects` row is tappable and lands on the index; it is not a
      decorative heading and it does not borrow the destination's ink while
      being inert.
- [x] The panel still starts at the shell's edge inset, fills its height and
      does not span the window (8.1's geometry scenario, with its cell-density
      assertions replaced by the stack assertions above).

## Risks / notes

- **This is a switcher, not a second Projects screen.** The sidebar shows names,
  not counts, not task lists, and it does not duplicate the row actions (edit,
  delete). The moment it grows those, it is a second copy of the project list
  and will disagree with the real one.
- **No "top 3".** A truncated list in permanent chrome needs a "why these three"
  rule and a "see all" affordance; a scrollable list needs neither, and the
  picker's ordering is already the honest answer to "which first". Capping the
  *visible height* while keeping the list scrollable is not a top-3: the rule
  stays "all of them, in the picker's order".
- **No per-project tree.** Rejected in review: it repeats Board/Backlog/Sprints
  under every project, and it implies per-project view state the router does not
  have (one active project, one active tab). A second level that says the same
  three words under every parent is a segmented control drawn as a tree.
- **The sidebar is drawn on Settings too.** That is deliberate — it is a project
  switcher, not part of the project-scoped tabs — and it is why the tap targets
  Board explicitly.

- **Gotchas:** `SIDEBAR_DENSITY` is load-bearing for the sidebar scenarios —
  remove it and they fail on composition, not on an assertion. The list tag is
  `shell.sidebar.projectList`, deliberately not `shell.sidebar.projects`, which
  is the Projects destination's tag; sharing it made every query for either
  match two nodes. Do not sort or filter in the view; both rules live in
  `ProjectPickerModel.reload()`. `weight(1f, fill = false)` is load-bearing
  twice: `fill = false` wraps a short list, the weight stops a long one from
  measuring unbounded. Any `weight` after the scoped group reintroduces the
  bottom-anchored layout.
