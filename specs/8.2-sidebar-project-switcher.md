# 8.2 — List and switch projects in the wide sidebar

- **status:** pending
- **priority:** P1
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §8, entry `8.2`. Depends on 8.1; the
  sidebar must exist before it can carry a list.

## Scope

- `:shared-ui` production and test sources. The project list is read through
  `ProjectPickerModel` from `:packages:feature-projects-presentation`, which
  `NavigationHost.kt` already imports and composes for the scoped-tab picker — no new
  dependency edge, no architecture-graph change.
- **No `:packages:design-system` edit.** The section heading reuses
  `Res.string.tab_projects` ("Projects"), which is the same word and the same meaning;
  the rows reuse `ttTypography`, `ttLabelSecondary`, `ttSelectionWash`, `ttIcon` and
  `ttText`. If Phase 2 finds it genuinely needs new copy, that is a `strings.xml` edit in
  the design system and a **drift**, not a silent addition — re-plan and ask.
- **No new state.** The highlighted row is `router.state.activeProjectID`; tapping a row
  is `router.openProject(id, AppTab.Board)`. Nothing in the sidebar remembers a
  selection of its own.
- Not cross-repo.

## Files

- `shared-ui/src/commonMain/kotlin/com/tasktracker/sharedui/NavigationSidebar.kt`
  — the section below the five destinations: heading, a `LazyColumn` of project rows
  with `weight(1f)`, active-row highlight, and `SidebarProjectTag(projectID)`. A long
  name ellipsises rather than widening the panel. The signature grows to carry
  `repository`, `activeProjectID` and `onOpenProject`, and the panel remembers and
  observes its own `ProjectPickerModel` (`remember` + `DisposableEffect`) so the observer
  is disposed with the chrome when the layout class changes.
- `shared-ui/src/commonMain/kotlin/com/tasktracker/sharedui/NavigationHost.kt`
  — the `Sidebar` arm passes `environment.repository`, `navigation.activeProjectID`, and
  `{ id -> router.openProject(id, AppTab.Board) }`. No model, no sorting, and no
  selection state is added to the host.
- `shared-ui/src/commonTest/kotlin/com/tasktracker/sharedui/ShellScenarios.kt`
  — the scenarios and their three host entry points.

## Contract

- [ ] The section lists exactly the **non-archived** projects, in `ProjectPickerModel`'s
      own order: `updatedAt` descending, then name. The first row is the most recently
      updated seed, pinned against a fixture where that is not the alphabetical first —
      otherwise an alphabetical list passes.
- [ ] Exactly one project row is highlighted, and it is the active project. On first
      composition with no active project, no row is highlighted.
- [ ] Tapping a row makes that project active and lands on **Board**, from any tab. A
      test that only asserts "a board appeared" is not enough: assert the `Board`
      destination and the row highlight together, so a stale id or a tab that did not
      move both fail.
- [ ] Tapping a project while **Settings** is selected still lands on Board. This is why
      the call is `openProject(id, AppTab.Board)` rather than the default
      `openProject(id)`: the router rejects Settings outright (`Router.openProject`'s own
      KDoc), and a switcher that silently does nothing on one tab is worse than one that
      moves.
- [ ] The highlight follows a project chosen **elsewhere**. Select a project from the
      Projects tab's list at 1280dp, then assert the sidebar's highlighted row moved to
      it. This is the assertion that fails if a second "which project" state is
      introduced.
- [ ] An empty repository renders no heading and no rows, and the five destinations are
      still there. No placeholder, no empty-state copy — the chrome should not explain
      the absence of data.
- [ ] Creating a project through the existing New Project sheet while the shell is up
      makes it appear in the section without a relaunch (the model observes
      `ProjectChange`). If the scenario's repository fixture cannot emit a change, record
      that as a coverage gap in `## Handoff` rather than delete the contract line.
- [ ] Twenty projects scroll inside the section and never push the five destinations off
      the panel: the destination row's bounds are unchanged before and after scrolling to
      the last project.
- [ ] Mutation checks: removing the tap handler turns the Board-landing scenario red;
      reversing the sort turns the first-row assertion red; replacing
      `router.state.activeProjectID` with a local remembered id turns the
      selected-elsewhere scenario red.

- **Gotchas:** do not sort in the view and do not filter in the view. Both rules already

  a second answer that drifts the first time project ordering changes. Dispose the
  observer when the class leaves composition, or a resize back to `Expanded` leaks an
  observer per crossing.

## Risks / notes

- **This is a switcher, not a second Projects screen.** The sidebar shows names, not
  counts, not task lists, and it does not duplicate the row actions (edit, delete). The
  moment it grows those, it is a second copy of the project list and will disagree with
  the real one.
- **No "top 3".** A truncated list in permanent chrome needs a "why these three" rule and
  a "see all" affordance; a scrollable list needs neither, and the picker's ordering is
  already the honest answer to "which first".
- **The sidebar is drawn on Settings too.** That is deliberate — it is a project
  switcher, not part of the project-scoped tabs — and it is why the tap targets Board
  explicitly.
- **Reusing `tab_projects` as the heading is intentional.** Same word, same meaning; a
  new identical string would be a second resource to translate and keep in sync.
