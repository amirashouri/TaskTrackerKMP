- **status:** Done
- **priority:** P2
- **plan:** `none` — follow-up to §11. The server half is
  [`TaskTrackerServer/specs/t10.6-agent-settings.md`](../../TaskTrackerServer/specs/t10.6-agent-settings.md).
  ACKed 2026-11-04 with the 3-bullet path map; the drift note below records the
  files the map did not name.

## Scope

An account can pair an agent machine with `tt agent connect`, but the app had no
surface that said whether one was available. A member dispatched a task into a
queue nobody might be servicing, and an administrator could only retire a machine
permanently with `tt agent disconnect`.

This task adds one Settings block:

1. **Status, for every signed-in user.** The Agent row says `Not set up`,
   `Running`, `Offline` or `Stopped`, and each live machine gets a row with its
   name and `provider · model`.
2. **Commands, for an administrator.** Stop and start per machine, and a
   "Set up agent" sheet with the exact `tt agent connect --server …` and
   `tt agent run` commands to run on the machine that holds the code.

The status is per account because pairing is: `GET /v1/agent/runners` is the
caller's own machines. There is no shared fleet in this slice, and the server's
claim scope is deliberately the runner owner's own runs.

Out of scope:

- No token minting in the app. `tt agent connect` logs in and the server returns
  the runner token once to that process; the app has no route to hand a token to
  a CLI, so showing one would be a credential nobody can adopt.
- No remote process start or kill. "Stop" is the server's claim gate.
- No polling while the tab is closed; the block reads when Settings opens.

## Contract

Wire (additive to `GET /v1/agent/runners` and the stop/start responses):

```json
{
  "id": "66666666-6666-6666-6666-666666666666",
  "name": "dev-machine",
  "provider": "openai-compatible",
  "modelLabel": "llama3.1",
  "lastSeenAt": "2026-11-03T12:00:00Z",
  "pausedAt": "2026-11-03T12:05:00Z",
  "createdAt": "2026-11-03T11:00:00Z"
}
```

- [x] `GET /v1/agent/runners` decodes into `AgentMachine`; every optional key has
      a default, `createdAt` is required, and a renamed required key fails to
      decode (`HttpAgentRunnersRemoteTest`).
- [x] `stopAgent` posts to `/stop` and `startAgent` to `/start`, and both read the
      confirmed row rather than guessing
      (`HttpAgentRunnersRemoteTest.stopAndStartPostToTheTwoPathsAndReadTheConfirmedRow`).
- [x] "Running" is a freshness question: a machine is running only when it is not
      paused and `lastSeenAt` is within two minutes of the snapshot's
      `observedAt`; all-live-paused is `Stopped`; no live machine is `Not set up`
      (`SettingsModelTest.openingSettingsReadsTheAgentOverview`,
      `LiveSettingsServiceTest.openingSettingsReadsTheFleetWithTheObservationTimeItWasJudgedAt`).
- [x] An agent read failure keeps the last snapshot and does not throw, because
      Settings must open offline (`LiveSettingsServiceTest.aFailedAgentReadKeepsTheLastSnapshot`).
- [x] A stop/start folds the server's row into the snapshot without a second GET,
      and a refused command leaves the row where it was and raises
      `agentFailure` (`LiveSettingsServiceTest.stoppingAMachineFoldsTheServersRowIntoTheSnapshot`,
      `SettingsModelTest.aRefusedAgentCommandHoldsTheFailureRatherThanThrowing`).
- [x] Cancellation is rethrown, not recorded as a failure
      (`SettingsModelTest.aCancelledAgentCommandIsRethrownRatherThanArmedAsAFailure`).
- [x] With no gateway, an agent command is a `Validation` failure rather than a
      silent success (`LiveSettingsServiceTest.anAgentCommandWithoutAGatewayIsRefused`).
- [x] A member sees the status row and neither command; an administrator sees
      Stop (or Start) for the machine and the Setup row, and the sheet opens and
      closes (`SettingsScenarios.theAgentStatusIsVisibleToAMemberWithoutCommands`,
      `anAdminStopsAMachineAndCanOpenSetup`).
- [x] Each setup command sits on its own numbered card and Copy puts exactly the
      text beside it on the clipboard, address included, with the app's one
      "copied" confirmation (`SettingsScenarios.theSetupCommandsCopyTheTextTheyShow`).
- [x] A failed command renders a dismissible banner
      (`SettingsScenarios.theAgentFailureIsADismissibleBanner`).

## Non-goal

- Do not add a Room table or offline queue for agent state. A pause is a
  server-owned fact; caching it would let the screen show a stop the worker never
  observed.
- Do not gate dispatching a run on this block. `projects.agentEnabled` and the
  server's dispatch preconditions remain the authority.

- **Pending:** the full three-host matrix and baseline regeneration; a rendered

  scenarios prove the nodes, the copied strings and the ordering, not wrap or row
  density).
- **Next step:** run `scripts/check.sh full` in `TaskTrackerKMP`, then regenerate
  `test-baseline.json` and record the delta here.
- **Gotchas:**
  - `ignoreUnknownKeys` is off. `pausedAt` is declared; any further runner key
    needs a client default first, in a released build.
  - The freshness window is client-side because the server touches `lastSeenAt`
    on every claim long poll and never answers "running" itself. Do not move the
    rule to the server without changing the wire contract.
  - Stop is a claim gate. The setup sheet deliberately says the process is the
    customer's; a stopped row with a live `tt agent run` is not a bug.
  - The Agent row is visible to members by design; only the commands are
    admin-gated, and the server enforces the same gate on the routes.
  - `SettingsPort` is implemented in four test doubles/preview ports. A new port
    method needs all of them, or those modules stop compiling.
  - `settings_agent_empty_state` ("Not set up") and `settings_agent_empty`
    ("No machine has been paired yet.") are two strings on purpose: the row's
    value and the block's explanatory line must be free to change separately.

## Risks / notes

- **Two sources of "stopped".** The server's `pausedAt` and the process actually
  running are independent. A paused row whose process is still alive is correct;
  an unpaused row whose process exited reads Online for two minutes and then
  `Offline`. The section says the status it can prove, not the one it would like.
- **A member's status is narrow.** Runners are per account, so this block says
  "your machine", not "the workspace's fleet". A shared fleet is a server contract
  change (`--shared` in the runner spec) and is not this task.
- **The setup sheet is instructions, not pairing.** It names the in-use root, not
  a saved preference the running clients have not taken, and it offers no token
  because the CLI has no route to adopt one.
