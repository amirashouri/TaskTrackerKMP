# 8.1 — Give the wide shell a sidebar instead of a rail

- **status:** pending
- **priority:** P1
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §8, entry `8.1`. The active index is
  the *what*; this file is the *how*.

## Scope

- `:shared-ui` production and test sources. One module, no new dependency edge.
- **No `:packages:design-system` edit.** The panel is assembled from primitives that
  already exist and are already measured: `Modifier.ttGlassSurface`, `ttRadius.surface`
  (16dp), `ttSpacing`, `ttTypography`, `ttSelectionLabelInk`, `ttSelectionWash`,
  `ttIcon`, `ttText`. No new colour, alpha, fill ramp, radius, or string, so no
  `strings.xml` change and no new token.
- **No `:packages:routing` edit.** The sidebar's selection is
  `router.state.selectedTab` and a tap calls `router::selectTab`, exactly as the rail
  does.
- Not cross-repo: nothing on the wire changes, so the dual-repo ACK does not apply.
  This is the in-repo ACK'd surface; what 5.3 did for two classes, this does for three.

## Files

- `shared-ui/src/commonTest/kotlin/com/tasktracker/sharedui/ShellLayoutClassTest.kt`

- `shared-ui/src/commonTest/kotlin/com/tasktracker/sharedui/ShellScenarios.kt`

## Contract

- [ ] `ShellLayoutClass.forWidth` resolves 839.5 → `Compact`, 839 → `Compact`,
      840 → `Expanded`, 1119.5 → `Expanded`, 1120 → `Sidebar`. `>=` is pinned against
      `>` at each boundary by at least one fractional width.
- [ ] `ShellSidebarMinimumWidth` is the **expression**
      `ShellExpandedMinimumWidth + ShellSidebarWidth`, not a copied literal, so moving
      either input moves the boundary. `ShellSidebarWidth == 280.dp` is pinned by an
      exact-value test, and `isWide` is true for `Expanded` and `Sidebar`, false for
      `Compact`.
- [ ] At 1280dp the shell composes the sidebar, and no rail and no bar. At 1000dp it
      still composes the rail, and no sidebar and no bar — the regression guard, because
      1000dp is where every existing wide scenario lives. At 390dp the bar alone.
- [ ] The sidebar is a **leading column, not an overlay**: at 1280dp the projects list's
      left edge is at or past the sidebar's right edge, read from
      `ProjectsListScreenTag` (the padding box is anonymous, so a node inside it is the
      only thing that shows the inset reached the pixels).
- [ ] Resizing 1280 → 1000 → 1280 draws exactly one chrome at each width and leaves no
      stale leading band. This is `shrinkingTheWindowPastTheThresholdShedsTheRailInset`
      extended to three classes: the ordering is chosen so both crossings are exercised
      on one composition, because a rail/sidebar that leaves the composition is never
      remeasured to zero.
- [ ] Exactly one destination row carries `semantics { selected = true }` and
      `Role.Tab`, and after tapping a row the selected row is the router's selected tab.
      Two assertions, as 5.2 settled on: a marker that never moves and a marker that
      falls off both satisfy "it is selected somewhere".
- [ ] Every `Expanded` comparison now means `isWide`, observed from the outside rather
      than by reading the source: at 1280dp the Sprints tab draws its list and detail
      side by side (`list.right < detail.left`, the 5.4 probe), and the New Project sheet
      is a centred window — its bottom edge sits clear of the shell's bottom edge rather
      than on it. Those two pin `SprintTwoPanes`, `LocalSheetPresentation`, and
      `LocalTabBarScrollUnderInset`'s zero under the new class.
- [ ] Mutation checks, each must turn its named scenario red: composing the rail instead
      of the sidebar at 1280; reverting one `isWide` site to `== Expanded` (the Sprints
      pair or the sheet assertion); removing `semantics { selected }` from the rows;
      removing the measured inset and hardcoding `280.dp` (the bounds assertion must
      catch a panel that draws 280 while measuring something else).

## Validation

- Run: `scripts/check.sh full` — a layout/rendering change, so iOS is required.
- Counts: the new `commonTest` scenarios and the enum tests run on all three hosts and
  move all three totals. Regenerate with `scripts/test-baseline.py`; `check-baseline.sh`
  must pass.
- **No pixel test.** No colour, alpha, fill ramp, radius, or hairline value is introduced
  or changed. The panel is `ttGlassSurface` at `ttRadius.surface`, which is the same
  primitive-and-radius pair the glass card already draws and measures; the only new thing
  is the panel's aspect ratio, which is a layout property, not a composite one. So the
  contract is structural and `test-reviewer` is not required. If Phase 2 introduces a new
  wash alpha, radius, or fill, that converts this task into a dual-host pixel test and a
  `test-reviewer` pass — record the conversion in `## Handoff` rather than shipping an
  unmeasured number.

  zero occurrences outside comments.

## Risks / notes

- **280dp and 1120dp are one decision.** The sidebar is wide enough for a project name;
  the content it leaves at the threshold is exactly the 840dp that
  `ShellLayoutClass`'s own KDoc already calls the narrowest genuine list-detail pair.
  Lowering 1120 without lowering 280 breaks the Sprints pair at the boundary — which is
  why the constant is an expression.
- **The rail is deliberately unchanged at 840–1119dp.** Its 146dp cells are the reason
  this task exists, but changing its geometry is task 8.3 and a separate PR. Do not
  adjust `TTGlassNavigationRail` here.
- **No lens.** A selection lens sliding down a list is the effect
  `ttSelectionWash`'s KDoc already rejects; the sidebar selects with the wash, not with
  travel.
- **Rows are content-sized** from `ttSpacing`, not from a new row-height token, for the
  same reason the rail's cells are: there is no existing height token that means "a
  navigation row", and inventing one here would be the guess the design-system rules
  forbid.
- **Android cannot express 1280dp** (its host viewport is 1024dp). Gate the new
  scenarios on `desktopWidthIsExpressible(1280)` exactly as the existing wide scenarios
  do, and keep one compact-width scenario ungated so the Android host still guards its
  own path.
- **The tag spaces stay distinct.** `SidebarButtonTag` is prefixed `shell.sidebar.`, not
  reused from `NavigationRailButtonTag` or `TabButtonTag`: a mixed-up query should find
  nothing rather than drive the wrong chrome, which is the reason 5.3 gave for the rail's
  own prefix.
