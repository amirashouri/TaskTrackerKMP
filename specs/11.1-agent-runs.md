# 11.1 — Agent runs: dispatch a task to a connected agent and follow its progress

- **status:** done
- **priority:** P1
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §11, entries `11.1`–`11.2`.
  This file is the client half of a dual-repo contract. The server half is
  [`TaskTrackerServer/specs/t10.1-agent-runs.md`](../../TaskTrackerServer/specs/t10.1-agent-runs.md);
  the two must agree key for key before either is implemented.

## Scope

Two surfaces, both attached to a work item:

1. **Dispatch.** A work item in `in_progress` offers "Send to agent". The request
   creates a server-side run; the agent itself runs elsewhere
   (`tt agent run`, on the machine holding the code).
2. **Progress.** While the run is live, the item's editor shows its status, the
   latest step, the event log, elapsed time, and a Cancel action.

What this task deliberately does **not** do:

- **No sync-envelope change.** Agent state is server-owned and polled, not
  merged. Nothing is added to the `workItem` payload — `ignoreUnknownKeys` is
  off, so a new key there breaks every installed build.
- **No Room table.** A run cannot progress offline, so v1 holds live state in
  memory only. Caching the last finished run is a later task, with its own
  migration and `packages/database` change.
- **No new Gradle module.** The surface lives inside `feature-projects-*`; an
  `feature-agent-*` triple is extracted only if a standalone screen arrives.
- **No agent write-back.** The run's summary is displayed; the user applies any
  status change themselves.

## Contract

The client declares exactly the keys the server sends. A property without a
default is required; `runnerId`, `startedAt`, `finishedAt`, `summary`, `error`
are declared with defaults because the server may omit them.

### DTOs

```kotlin
@Serializable
data class AgentRunDto(
    val id: AgentRunID,
    val workItemId: WorkItemID,
    val projectId: ProjectID,
    val status: AgentRunStatus,
    val requestedBy: UserID,
    val runnerId: AgentRunnerID? = null,
    val cancelRequested: Boolean = false,
    val createdAt: Instant,
    val startedAt: Instant? = null,
    val finishedAt: Instant? = null,
    val summary: String = "",
    val error: String = "",
)
```

Timestamps use `Instant` through the shared `DateCoding` (ISO-8601 UTC, whole
seconds), not raw strings.

- [x] `POST /v1/agent/runs` dispatches with the item's id; a `409` surfaces as
      "already running" rather than a transport error, and does not dead-letter
      anything or touch the outbox (`HttpAgentRunsRemoteTest.dispatchPostsTheItemIdAndReadsTheRun`,
      `AgentRunModelTest.aSecondDispatchIsReportedAsAlreadyRunning`; the port has
      no outbox dependency at all).
- [x] Polling uses `afterSeq`: an event already applied is never appended twice,
      and an empty page leaves the log untouched
      (`AgentRunModelTest.followPollsUntilTheRunIsTerminal`).
- [x] Polling stops on `succeeded`, `failed` and `cancelled`, and the loop is tied
      to the sheet's composition through the host's `LaunchedEffect`
      (`AgentRunModelTest.followPollsUntilTheRunIsTerminal`,
      `pollingStopsOnAFailedRunToo`).
- [x] Cancel sends one request, shows the run as cancelling, and only reports
      `cancelled` when the server says so — cancel is cooperative
      (`AgentRunModelTest.cancelAsksOnceAndShowsTheRequestUntilTheServerCancels`).
- [x] The server's `run` and `event` key sets decode with `ignoreUnknownKeys`
      off; a renamed or missing key fails to decode
      (`HttpAgentRunsRemoteTest.aRenamedServerKeyFailsToDecode`,
      `theOptionalKeysMayBeOmitted`). The `runners` key set is not declared by
      the app: pairing and revocation live in `tt agent`, and the app never calls
      those routes.
- [x] Nothing is written to the outbox, and no existing DTO gains a field: the
      remote depends only on `HttpClient`, and every new DTO is private to
      `HttpAgentRunsRemote`.
- [ ] A structural UI test for `WorkItemAgentSection` — not written in this pass;
      see `## Handoff`.

- **Pending:** the structural UI test for the section; the three-host matrix
  (`scripts/check.sh full`) and the baseline regeneration. A demo graph (no API
  root) has no agent port, so the section is absent there — intended, but it is
  only compile-checked.
- **Next step:** write `WorkItemAgentSection` structural scenarios against the
  sheet (status pill, step text, Cancel presence while live, absence when the
  item is not in progress), then run the full matrix and regenerate counts.
- **Gotchas:**
  - `ignoreUnknownKeys` is off. A key the client does not declare is a decoding
    failure, not a skipped value — adding one to a running server breaks the app.
  - The agent API is `camelCase`, unlike the auth/admin half, because it is
    entity-shaped and carries ISO-8601 timestamps.
  - `AgentRunModel` must not poll while off-screen; the existing models expose
    their polling only while the sheet is composed.
  - Polling a run in a background service is out of scope. The user sees a run's
    final state when they reopen the item, from the list endpoint.

## Risks / notes

- **A run outliving the app** is normal, not an error: the server keeps the
  terminal state, and the editor's `GET /v1/agent/runs?workItemId=…` recovers
  it. Do not invent a local "in flight" flag.
- **A 404 on a run** means the server pruned it; show the summary as no longer
  available rather than a retry loop.
- **Cancel latency** is up to one heartbeat (about 10 s). The UI needs a
  "cancelling" state so a button that appears to do nothing for ten seconds is
  not read as broken.
- **The event log is untrusted text** from a model. Render it as plain text,
  never as markup or a link the model chose.
