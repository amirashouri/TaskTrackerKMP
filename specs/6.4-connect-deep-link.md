## Scope

`:packages:routing` (the grammar and the carrier), `:shared-ui` (dispatch), and both
platform shells (delivery). This is the half the server's `tt install` renders into a QR
code, so the grammar is a **shared contract** and needs the dual-repo ACK even though no
DTO changes.

The client is the fixed point: the server half (T9.7) must use this grammar byte for byte.

## Contract

- [x] `tasktracker://connect?url=https%3A%2F%2Ftasks.example.com` parses to Settings with
      `serverAddress == "https://tasks.example.com"`.
- [x] A missing, empty, or malformed-percent-escape `url` is **rejected**
      (`route()` returns null), not routed to Settings with a blank or altered field. A
      link that silently does nothing is worse than one the parser refuses.
- [x] The value is percent-decoded exactly once — a URL containing its own `%` sequence
      survives (`%2F` inside the path stays `%2F`, not `/`). Double-decoding is the classic
      bug here and it turns a valid URL into a different one.
- [x] A path instead of a query (`tasktracker://connect/…`) is rejected; the grammar is
      one shape, not two.
- [x] Scheme policy, reachability, and normalisation stay with 6.3's
      `CheckServerAddress`: the parser decides whether the *link* is well formed, not
      whether the *server* is usable.
- [x] Signed in, the link lands on Settings with the address waiting; the editor opens
      once with it prefilled, and the pending value is cleared.
- [x] Scanned while signed out, the link is **buffered**, not rejected: `enterMain` lands
      on Settings, the editor opens, and the address is consumed. Every other link keeps
      the existing signed-out reject.
- [x] An unconsumed address survives an unrelated link and is discarded on a real
      sign-out; an already-signed-out `enterAuth` (the launch restore) does not discard it.
- [x] The link's address wins over the saved override and the in-use root.
- [x] Android and iOS both deliver URLs to the shared sink, including a cold start where
      the URL arrives before Compose has a collector.
- [x] Every existing link in `RoutingTest` still parses to the same state — the new case
      must not change `split`'s behaviour for any of them.
- [x] Android's cleartext allow-list is **not** widened for plain-HTTP LAN; the documented
      limitation stands.

## Handoff

- **Done:** grammar (`connect`, strict one-decode), `ParsedLink.serverAddress`,
  `RouterState.pendingServerAddress`, signed-out buffering, `enterMain` landing on
  Settings, one-shot consumption and sign-out discard, Settings prefill precedence,
  `DeepLinkSource` + `receiveDeepLink`, `RootScreen` collector, shell scenario,
  Android filter/`singleTop`/`onCreate`/`onNewIntent`, iOS `.onOpenURL`, spec and PLAN
  entry. Full three-host gate and all four mutation checks passed; baseline regenerated.
- **Pending:** commit, push, PR, merge. The server half (T9.7) follows on its own branch.
- **Next step:** branch `feat/6.4-connect-deep-link` → PR to `main`; then server T9.7
  (`cmd/tt/connect.go`, `install.go`, `go.mod`/`go.sum`, spec, PLAN) using this exact
  grammar: `tasktracker://connect?url=<url.QueryEscape(verifiedURL)>`, and print the link
  only when the active provider has a verified URL, otherwise a `run tt expose` hint.
- **Gotchas:**
  - `DeepLinkParser.split` lowercases path segments and strips `?`/`#`; the `connect`
    arm must read the raw URL, and the fragment must be stripped *before* looking for the
    query mark.
  - `RouterState.clearedNavigation()` only clears paths, which is why
    `pendingServerAddress` survives `enterMain` without a second copy.
  - `SettingsDestination` is reached from the tab root and from a pushed
    `AppRoute.Settings`; only one composes, and the first to see a pending address
    consumes it.
  - The Kotlin top-level function is exported to Swift as
    `DeepLinkSourceKt.receiveDeepLink(url:)` (the file name, not `MainViewControllerKt`).
  - `tt` must percent-encode the **whole** URL (`url.QueryEscape`), including `&`, or the
    client's one decode produces a different address.

## Risks / notes

- Easy to get wrong: accepting the URL and trusting it. The link is a *prefill*, and 6.3's
  validator is what decides whether it is usable — a link that saves an unreachable
  address produces a sync failure days later, which is the outcome 6.3 exists to prevent.
- The server's `tt` must render the same grammar. If this task changes the parameter name,
  `T9.7` changes with it in the same MR or the two halves ship disagreeing.
- The custom scheme is inherently claimable by another app; this is a prefill into a field
  the user confirms, not an automatic trust decision.
