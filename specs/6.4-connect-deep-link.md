# 6.4 — `tasktracker://connect?url=…` pairing link

- **status:** pending
- **priority:** P0
- **plan:** [`docs/PLAN.md`](../docs/PLAN.md) §6 — Server connection, entry `6.4` — the
  *what* and the rationale live there; this file is the *how*.

## Scope

`:packages:routing` (the grammar) and `:shared-ui` (dispatch). This is the half the
server's `tt install` renders into a QR code, so the grammar is a **shared contract** and
needs the dual-repo ACK even though no DTO changes.

## Files

To confirm at Phase 1.

- `packages/routing/.../DeepLinkParser.kt` — a new root case, `connect`, that reads a
  `url` query parameter. The parser is currently host-and-path only (`split(url)` then
  `components[root]`), so a query string is a genuinely new case rather than a new arm:
  confirm how `split` treats `?` before writing the branch.
- `packages/routing/.../Routes.kt` — if the link needs a route rather than a tab + path;
  `ParsedLink` already carries `(tab, route, path)`, and Settings is a tab, so prefer
  landing on Settings with the value carried in the path rather than adding a field.
- `packages/routing/src/commonTest/.../RoutingTest.kt` — one test per branch.
- `shared-ui/.../NavigationHost.kt` — dispatch to Settings with the URL prefilled. **Edit
  deliberately**, per `shared-ui/AGENTS.md`; this file is large and a scripted replace has
  bitten before.
- `packages/feature-settings-presentation/.../SettingsModel.kt` + screen — only if 6.2
  does not already expose a way to prefill. If 6.2 lands first, this may be a no-op there.

## Contract

- [ ] `tasktracker://connect?url=https%3A%2F%2Ftasks.example.com` parses to Settings with
      the decoded value.
- [ ] A missing, empty, or unparseable `url` is **rejected** (`route()` returns null), not
      routed to Settings with a blank field. A link that silently does nothing is worse
      than one the parser refuses.
- [ ] The value is percent-decoded exactly once — a URL containing its own `%` sequence
      survives (`%2F` inside the path stays `%2F`, not `/`). Double-decoding is the classic
      bug here and it turns a valid URL into a different one.
- [ ] An unknown host (`tasktracker://connect/…` with a path instead of a query) is
      rejected; the grammar is one shape, not two.
- [ ] Every existing link in `RoutingTest` still parses to the same state — the new case
      must not change `split`'s behaviour for any of them.

## Validation

- Run: `scripts/check.sh full` — `:shared-ui` and `:packages:routing` on all three hosts.
- Counts: regenerate `test-baseline.json`.
- Mutation check: with the `connect` arm removed, the parse test must fail on `null`.

## Handoff

- **Done:** the PLAN entry only. No code.
- **Pending:** the ACK (2+ modules, public API, shared-ui), then read `split` before
  designing the query handling.
- **Next step:** read `DeepLinkParser.split` and decide whether the query is stripped there
  or parsed in the `connect` arm. Do not change `split` for the other roots.
- **Gotchas:** `DeepLinkParser.route` is a pure function by design and every branch is
  tested without a platform. Keep it that way — a `URL` type here would make the grammar
  untestable on JVM, which is why the comment at the top of the file exists.

## Risks / notes

- Easy to get wrong: accepting the URL and trusting it. The link is a *prefill*, and 6.3's
  validator is what decides whether it is usable — a link that saves an unreachable
  address produces a sync failure days later, which is the outcome 6.3 exists to prevent.
- The server's `tt` must render the same grammar. If this task changes the parameter name,
  `T9.7` changes with it in the same MR or the two halves ship disagreeing.
