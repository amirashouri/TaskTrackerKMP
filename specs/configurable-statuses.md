# configurable-statuses — project-defined workflow statuses

- **status:** pending
- **priority:** P1
- **context:** `WorkItemStatus` is a fixed six-value enum
  (`packages/domain/.../Entities.kt`), board columns are derived from it, and the editor's
  status picker can only choose from it — so a sales, support, or design team cannot rename
  a stage or add one. This is the second "teams with different needs" gap from the
  `WorkItemEditor` review (2026-11-06). **Cross-repo wire change**: read `../AGENTS.md`
  §1/§2, needs a Phase 1 `ACK`, server lands first. Server side:
  `TaskTrackerServer/specs/configurable-statuses.md`.

## Scope

`:packages:domain` (the enum and its `isTerminal` / `appearsOnBoard` / `boardOrder`
predicates), `:packages:feature-projects-{domain,data,presentation}` (board, backlog,
editor, archive), `:packages:database` (merge/Room), and the network DTOs. Not custom
fields, hierarchy, or automations.

## Files

`to confirm at Phase 1` — prefer the **additive** shape below over replacing the enum.

- `packages/domain/.../Entities.kt` — add `StatusDefinition` (key, name, category, order,
  color) and `Project.statuses`; keep `WorkItemStatus` as the coarse **category**
  (Backlog/Todo/InProgress/InReview/Done/Closed) that the terminal/board rules read, and add
  `WorkItem.workflowStatusID` referencing the catalog. `boardOrder` / `appearsOnBoard` /
  `isTerminal` move from enum-derived to catalog-derived.
- `packages/feature-projects-presentation/.../projects/ProjectBoard*.kt` — columns from the
  project catalog, ordered; `statusLabel` mapping follows the catalog.
- `.../workitem/WorkItemEditor.kt` + `WorkItemEditorModel.kt` — `selectableStatuses` becomes
  the catalog; the picker and `Draft` follow the selected status.
- `packages/database`, `packages/feature-projects-data` — storage + merge for the catalog and
  the per-item reference, with a Room migration.
- Server (owned by its spec): `internal/db/migrations`, `internal/entities`, `cmd/server`,
  `docs/API.md`, `cmd/server/contract_test.go`.

## Contract

- [ ] A project admin can define ordered statuses, rename them, and choose a category; the
  board, backlog, and editor render the catalog instead of the hardcoded six.
- [ ] Existing behavior is preserved by **seeding** each project with the current six statuses
  (same order, same categories) on migration, so no item changes column or meaning.
- [ ] Done/Closed terminal and archive/overdue rules keep working, now derived from the
  status **category**, so renaming a status cannot change whether an item is overdue.
- [ ] Decoding is client-first: the client declares `statuses` and `workflowStatusID` with
  defaults; a server that omits them still decodes (`ignoreUnknownKeys` stays off).
- [ ] Reverting the client change fails a focused test that pins catalog-driven columns.

## Non-goal

- [ ] No transition rules / required-field gates per status (a separate automations spec).
- [ ] No per-team/per-user status visibility.
- [ ] No change to `Priority`.

## Validation

- Run: `./gradlew --offline :packages:<module>:jvmTest --tests '<pattern>'` for domain
  (category + terminal rules), database (migration/merge), and editor/board models; focused,
  under a minute. Server: `go test ./internal/...` per its spec.
- Cross-stack: a project with a renamed/added status survives a push/pull round-trip and
  renders the same on reload; the server contract test pins the client's key set.
- Counts: `test-baseline.json` moves on the JVM host; regenerated by a release
  `scripts/check.sh full`, not the focused run.
- Board/editor rendering changes are structural, not pixel-reading, unless a new swatch or
  colour token is introduced — then run the pixel test through `test-reviewer`.

## Risks / notes

- Changing `status` from an enum to a free key is a **breaking** wire change; the additive
  category + catalog reference avoids it and should be the default plan. Only version-bump
  (`/v1`) if the additive shape proves unworkable.
- Two clients generating catalog entries for the same project offline is the merge hazard —
  the server owns the catalog; a client create must round-trip through sync like a tag does.
